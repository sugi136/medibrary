# 마이메디 코드 품질 및 책임 분리 점검 보고서

## 결론

현재 구현은 **요구사항 기반 초기 골격으로서는 계층과 기능의 큰 경계가 비교적 잘 잡혀 있습니다.** 특히 백엔드는 Controller–Service–Repository–Adapter 분리가 명확하고, 외부 API 호출을 `adapter` 패키지에 제한한 점이 좋습니다. 반면, 일부 서비스에 검색 전략·캐시·인증 사용자 조회가 함께 들어가 있고, 프론트엔드는 화면 컴포넌트가 API 호출·상태 관리·표현·스타일을 동시에 맡는 구조입니다. 따라서 현 상태를 “기능 구현을 시작하기에 좋은 구조”로는 평가할 수 있으나, **클린 코드와 유지보수성 측면에서 완성도가 높은 상태는 아닙니다.**

| 평가 영역 | 평가 | 판단 |
|---|---:|---|
| 백엔드 클린 코드 | 6.5 / 10 | 명명과 계층 구조는 양호하나 서비스 책임 과밀, 예외·트랜잭션·테스트가 보완되어야 합니다. |
| 백엔드 책임 분리 | 7 / 10 | Controller, Service, Repository, Adapter의 상위 계층 분리는 적절합니다. |
| 프론트엔드 클린 코드 | 5.5 / 10 | API 모듈과 스토어가 있으나 페이지 SFC가 비대하고 표현·로직이 결합되어 있습니다. |
| 프론트엔드 책임 분리 | 5 / 10 | 라우터·API·인증 스토어는 분리되어 있지만, 도메인별 composable과 재사용 UI 컴포넌트가 부족합니다. |
| 초기 프로젝트로서의 종합 적합성 | 6 / 10 | 미니 프로젝트의 출발점으로는 적합하지만, 실제 연동 및 기능 확장 전에 정리가 필요합니다. |

> 현재 구조는 “무작정 한 파일에 모든 기능을 넣은 코드”는 아닙니다. 다만 화면 수와 외부 연동이 늘어나면 빠르게 복잡해질 지점이 이미 보입니다.

## 잘 분리된 부분

백엔드는 `controller`, `service`, `repository`, `entity`, `dto`, `adapter`, `config`로 패키지를 나누어 HTTP 처리, 비즈니스 로직, DB 접근, 외부 API 접근을 구분하고 있습니다. `DrugController`는 검색·상세·부작용·DUR 요청을 해당 서비스로 위임하는 얇은 구조이며, 컨트롤러에 SQL·외부 HTTP 호출·도메인 판단이 섞이지 않았습니다. `EyakClient`, `OpenFdaClient`, `GranuleClient`, `DurClient`가 외부 API 주소와 JSON 응답 파싱을 맡는 것도 책임 경계상 올바른 방향입니다.

프론트엔드도 `router`, `stores`, `api`, `views`를 분리했습니다. 특히 `api/index.js`에 Axios 인스턴스와 엔드포인트 호출을 모으고, 라우터 가드가 인증이 필요한 `SCR-MY-001`, `SCR-DASH-001` 화면 접근을 담당한 점은 긍정적입니다. 화면 ID별 View 분리도 요구사항 정의서의 화면 구조와 잘 맞습니다.

| 긍정 요소 | 근거 | 효과 |
|---|---|---|
| 얇은 Controller | `DrugController`, `FavoriteController`, `AuthController`가 서비스 호출 위주로 구성됩니다. | HTTP 계층과 업무 로직이 뒤섞이지 않습니다. |
| 외부 연동 격리 | 공공 API와 openFDA 호출이 `adapter`에 배치됩니다. | 서비스 계층이 외부 API 세부 JSON 형식에 덜 의존합니다. |
| DTO 분리 | 요청·응답 객체가 Entity와 구분됩니다. | DB 모델이 API 계약에 직접 노출되지 않습니다. |
| 인증 구성 분리 | JWT 필터·토큰 제공자·Security 설정이 `config`에 있습니다. | 인증 관심사가 도메인 서비스에 섞이지 않습니다. |
| 프론트 API 모듈화 | 엔드포인트 호출이 `api/index.js`에 모여 있습니다. | URL과 HTTP 메서드의 중복이 줄어듭니다. |
| 라우팅 가드 | 인증 요구 화면이 라우터 메타데이터로 표현됩니다. | 화면별 인증 조건이 View 내부에 분산되지 않습니다. |

## 백엔드에서 우선 보완할 점

### `DrugService`의 책임이 넓습니다

`DrugService`는 이름·모양·색깔의 검색 분기, 로컬 검색, 외부 낱알식별 API 재조회, 외부 결과의 DB 캐시 저장, 상세 조회, 즐겨찾기 여부 판단, 현재 인증 사용자 추출까지 담당합니다. 기능상 연결되어 보이지만, 검색 정책·캐시 저장·인증 컨텍스트는 서로 변경 이유가 다릅니다.

`DrugSearchService`는 검색 전략과 결과 조합만 맡고, `DrugCacheService`는 외부 결과의 upsert만 맡으며, `CurrentUserProvider`는 `SecurityContextHolder` 접근을 캡슐화하는 편이 좋습니다. 그러면 약 상세 조회나 즐겨찾기 기능이 인증 구현 세부사항에 직접 의존하지 않게 됩니다.

### DB 트랜잭션 안에서 외부 HTTP 호출이 발생합니다

`DrugService.search()`와 `SideEffectService.getSideEffects()`는 `@Transactional` 범위 안에서 외부 HTTP 호출을 수행할 수 있습니다. 네트워크 대기 동안 DB 커넥션과 트랜잭션이 유지되면 응답 지연 시 커넥션 풀이 불필요하게 점유됩니다. 외부 API 호출은 트랜잭션 밖에서 실행하고, 필요한 캐시 저장만 짧은 쓰기 트랜잭션으로 분리하는 방식이 더 안전합니다.

### `DurService`의 조회 방식은 데이터가 늘면 비효율적입니다

`checkFavoritePairs()`가 전체 `dur_pairs`를 불러온 뒤 Java Stream에서 즐겨찾기 ID 목록과 비교합니다. 초기 데이터에는 문제가 없지만, DUR 캐시가 커지면 불필요한 행을 모두 읽게 됩니다. `drug_id_a IN (...) AND drug_id_b IN (...)` 조건을 가진 Repository 쿼리로 위임해야 DB가 필터링을 수행합니다.

### 예외 처리 정책이 분산돼 있습니다

서비스는 `ResponseStatusException`을 직접 만들고, 외부 어댑터는 넓은 `catch (Exception)` 뒤에 사용자 문구를 반환합니다. 이는 빠르게 동작시키기에는 편하지만, 오류 코드·로그·재시도 가능성·운영 추적이 한 정책으로 관리되지 않습니다. `BusinessException`, `ExternalApiException` 같은 도메인 예외와 `@RestControllerAdvice` 기반 전역 오류 응답을 두고, 어댑터에서는 원인 예외를 로그와 함께 보존하는 구조가 적절합니다.

현재 `exception` 패키지가 비어 있으므로, 이 부분은 실제 구현 전 우선 보완하는 것이 좋습니다. 외부 API가 실패했을 때 사용자에게 부분 실패 응답을 주는 정책 자체는 요구사항과 잘 맞으므로, 정책을 없애는 것이 아니라 **정책을 한 곳에서 일관되게 표현**하는 것이 핵심입니다.

### DTO와 매핑의 의미를 더 분명히 할 필요가 있습니다

`DrugSummary`는 검색 결과와 즐겨찾기 목록에 공용으로 사용되지만, `favoriteId`는 즐겨찾기 목록에서만 의미가 있습니다. nullable 필드를 늘리기보다는 `FavoriteDrugSummary`처럼 별도 응답 DTO를 두는 편이 API 계약을 더 명확하게 만듭니다. 또한 `FavoriteService`에 직접 DTO 생성 코드가 있고 `DrugMapper`에도 유사한 매핑이 있어, 매핑 규칙을 한 곳으로 모을 필요가 있습니다.

### 테스트와 시간 제한 설정이 부족합니다

실행 빌드는 통과하지만 서비스 단위 테스트, Repository 테스트, 외부 API 어댑터의 Mock HTTP 테스트가 없습니다. 또한 `application.yml`의 `app.external.timeout-millis` 설정값이 `RestClient`의 connect/read timeout에 실제 연결되어 있지 않습니다. 외부 API 지연을 3초 이내로 제한한다는 `REQ-N-003`을 충족하려면 `RestClient` 요청 팩토리 설정으로 이 값을 적용하고, 타임아웃·캐시 적중·매핑 실패를 테스트로 고정해야 합니다.

## 프론트엔드에서 우선 보완할 점

### `DrugDetailView.vue`가 여러 책임을 한 번에 맡습니다

상세 View는 약 상세 로딩, 탭 상태, 부작용 호출, DUR 지연 호출, 즐겨찾기 처리, 로그인 리다이렉트, 오류 상태, 네 개 탭의 템플릿, 화면 고유 CSS까지 포함합니다. 단일 파일 컴포넌트가 약 175줄이라고 해서 반드시 나쁜 것은 아니지만, 이 화면은 기능 확장 가능성이 가장 크므로 현재 형태로는 변경 충돌과 테스트 난도가 높아집니다.

다음과 같이 분리하는 것이 적절합니다.

| 분리 대상 | 권장 파일 | 책임 |
|---|---|---|
| 상세 조회 및 탭 상태 | `composables/useDrugDetail.js` | 약 상세·활성 탭·지연 조회 상태 관리 |
| 즐겨찾기 변경 | `composables/useFavoriteAction.js` | 로그인 검사, 등록·해제, 처리 상태 |
| 상단 약 요약 | `components/drug/DrugSummaryHeader.vue` | 제목·기본 외형·하트 버튼 표시 |
| 기본정보 탭 | `components/drug/BasicInfoPanel.vue` | 기본정보 렌더링 |
| 효능·복용 탭 | `components/drug/UsageInfoPanel.vue` | 효능·용법·주의사항 렌더링 |
| 부작용 탭 | `components/drug/SideEffectPanel.vue` | 국내·해외 카드, 로딩·오류 표시 |
| DUR 탭 | `components/drug/ContraindicationPanel.vue` | 금기/주의 목록, 전체 보기, 재시도 |

이 구조에서는 View가 “라우트 파라미터를 받아 조합하는 역할”만 하므로, 각 패널을 독립적으로 테스트하거나 재사용하기 쉬워집니다.

### 오류 처리와 사용자 메시지가 각 View에 흩어져 있습니다

`SearchView`, `DrugDetailView`, `FavoritesView`, 인증 화면이 각자 Axios 오류를 해석하고 한국어 메시지를 직접 구성합니다. 오류 메시지는 UX상 세부 화면에 맞춰 다를 수 있으나, 네트워크 오류·401·403·500·타임아웃 같은 공통 규칙은 Axios response interceptor와 `normalizeApiError()` 유틸리티로 일원화하는 것이 좋습니다.

### 인증 토큰 저장 책임이 중복됩니다

`auth.js`와 Axios 인터셉터가 각각 `localStorage`를 직접 접근합니다. 현재는 같은 키를 쓰므로 기능상 문제가 크지 않지만, 토큰 저장 방식이 바뀌면 두 파일을 함께 수정해야 합니다. `tokenStorage.js` 유틸리티를 만들어 `getToken`, `setToken`, `clearToken`을 한 곳에서 제공하면 저장 매체의 변경을 안전하게 흡수할 수 있습니다.

### UI 재사용 단위가 부족합니다

약 카드, 비어 있는 상태, 로딩 상태, API 오류 문구, 패널 카드가 여러 화면에서 유사하게 반복될 여지가 있습니다. 특히 검색 결과의 약 카드와 즐겨찾기 목록 항목은 `DrugCard.vue`로 공통화하는 것이 좋습니다. 현재 `FavoritesView`의 브라우저 기본 `confirm()`도 공통 `ConfirmDialog` 컴포넌트로 바꾸면 디자인·접근성·테스트를 일관되게 관리할 수 있습니다.

### 스타일 포맷과 타입 안정성이 보완 대상입니다

`DrugDetailView` 등 일부 `<style scoped>` 블록은 여러 선택자를 한 줄에 연결해 가독성이 떨어집니다. CSS 자체를 `components` 또는 `styles` 단위로 분리하거나, 최소한 한 선택자당 한 선언 블록으로 포맷을 맞추는 편이 좋습니다. 또한 JavaScript만 사용하므로 API 응답 속성 오타를 컴파일 단계에서 잡기 어렵습니다. 과제 요구가 JavaScript라면 JSDoc 타입 선언부터 도입하고, 확장 단계에서는 TypeScript 전환을 고려할 수 있습니다.

## 최종 판단

질문에 직접 답하면, **백엔드는 책임과 기능별 분리가 ‘대체로 잘 되어 있다’고 평가할 수 있습니다.** 계층 구조가 명확하고 외부 연동의 위치가 적절합니다. 그러나 서비스 단위의 책임을 더 잘게 나누고, 예외·트랜잭션·테스트를 정리해야 클린 코드 기준에서도 좋은 평가를 받습니다.

프론트엔드는 기본적인 디렉터리 분리는 되어 있으나, **View 중심 구현이 강해 책임 분리가 아직 충분하지 않습니다.** 특히 상세 화면을 composable과 탭별 컴포넌트로 분해하는 작업을 먼저 수행하면 개선 효과가 가장 큽니다.
